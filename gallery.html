COMICZOMBIES

A GAME THAT DRAWS ITSELF

A Call-of-Duty-style round-based zombies shooter that runs in a browser tab, styled like a graphic novel. Heavy ink, halftone screen-tone, saturated flats — and not one downloaded asset. No models. No textures. No audio files. No webfonts.

Every mesh is built from code, every texture is painted to a canvas at boot, every sound is synthesised from oscillators and noise. The entire game is 43,645 lines of TypeScript and a single dependency, written with Claude Code in about a day.

How it was built

Not "one prompt, one game". The project runs like a small studio: a milestone is planned, agents build it in sequence, adversarial reviewers try to break it, a fix pass applies what they found, and then a human plays the result and says what's wrong. Their feedback outranks the plan. That loop ran six times in a day.

Agents verify facts — types, draw calls, allocation, hit registration. The human judges everything subjective. That split is deliberate: machines are good at "is this leaking", bad at "is this satisfying".

What the reviewers actually caught

The adversarial pass is where most of the quality comes from. A sample of real bugs it found, each of which had already passed its author's own tests:

Bug Why nobody saw it
Every zombie rendered translucent The depth prepass used a stock material that couldn't run the vertex shader posing the body. Two individually-correct decisions, broken only together.
Slide silently dropped on every kill Input edges died on frames that ran zero fixed steps — and hitstop, added later, opened exactly that hole on every kill.
Knockback was squared A units mismatch across a module boundary: 386 m/s of knockback threw a zombie 65 m, so every follow-up shot missed.
The player floated instead of falling grounded was only ever set true and never derived from the world. Measured: 0 of 17 ledges fell.
Every ground light pool was invisible Fan geometry wound the wrong way, so all 55 were backface-culled. Proven by A/B: "lights on" and "no lights at all" rendered bit-identically.

Nothing is downloaded

The constraint drives the art direction, not the other way round. Bold, flat, ink-outlined comic art is achievable in code at a quality that reads as premium — photorealism is not. So the style was chosen to fit the constraint, and then the constraint was never broken.

One dependency: three. Everything else is standard browser APIs.

The render pipeline

The comic look is not a filter bolted on at the end — it is the rendering architecture. Nine passes, in a fixed order, and the first three are never dropped by a quality tier because losing them loses the art direction.

One rule that fixed everything

Early builds made the playtester ill. Their words: "every pixel seems to be jumping like glitching." The diagnosis was a principle, not a bug — a comic page does not animate its own texture. Paper doesn't shimmer, halftone dots don't crawl, CMYK plates don't re-register every frame. Those things are printed.

Layer Rule
Halftone latticePerfectly static in screen space. Nailed to the page.
Paper grainStatic. One sheet, not a new one every frame.
Chromatic misregistrationOne constant offset per session — like one bad print run.
Boiling ink line12 fps, hero contours only, with a hard coverage budget.

The measurable version: with the camera parked, consecutive frames must differ by under 0.5% of pixels. It went from 24.77% → 0.065%. Stand still in the finished game and the image is frozen — only the world moves.
